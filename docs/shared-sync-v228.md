# v228: 初期100万CREDIT・自動REBET・BETとWINの残高管理

更新日: 2026-11-16  
版: `20261116-v228-credit-auto-rebet`

## 今回の仕様

ユーザー指定により、暫定の初期CREDITを1,000,000とし、AUTO REBETを初期状態でONにする。通常の全9ゲームでは各3,000、合計27,000をBETする。BET成立時に残高を一度だけ減らし、ゲーム終了時にWINを一度だけ加算する。精算が確認できてから、次のBET TIMEで同じ選択額を再BETする。

| 操作 | CREDIT |
| --- | ---: |
| 初期化 | 1,000,000 |
| 1回目の27,000 BET成立 | 973,000 |
| 1回目のWIN 5,000を精算 | 978,000 |
| 2回目の27,000 BET成立 | 951,000 |
| 2回目のWIN 7,000を精算 | 958,000 |

残高が次のBET額に満たない場合は自動REBETを停止し、BETボタンを無効化する。残高を超える増額ボタンも灰色で操作不可にする。残高とBETが同額の場合は参加でき、成立後は0になる。残高不足を理由にマイナスへ進めたり、自動で初期残高へ補充したりしない。

AUTO REBETはBET時計内のチェックボックスで切り替える。OFFの場合は「BETする」から、そのBET TIMEに限って手動参加できる。すでに成立したBETはチェックを外しても取り消さず、次回以降の自動参加を停止する。受付中の額は変更できるが、登録要求中・登録済みの額は固定する。

## CREDIT不足の原因

従来の標準構成は9ゲーム×3,000 BETだった一方、ゲーム本体の初期CREDITは1,000だった。さらに配当モジュールはlocalStorageに同じwallet revisionが記録されていると、再読み込み後の新しいゲーム本体へ残高を復元しなかった。実サーバー残高500,000・保存済みrevisionが同じケースでは、ゲーム内部が1,000のまま27,000を要求し、参加登録が0件になることを再現した。

今回、過去のページが確認したrevisionと、現在のページへ反映済みのrevisionを分離した。同じrevisionでも現在のページに未反映なら復元し、表示とBET判定で同じ残高を使用する。稼働中の別ラウンドへ古い財布を上書きすることや、精算ACKで結果演出をresetすることは避ける。

また、全BETを0にしても過去の27,000を復元する処理を削除した。次ゲームの額は現在の `bets` に統一し、`locked`・`enabled`・ゲーム別のサーバー送信内訳も同じ選択から作る。

## サーバーでの残高管理

- walletのcreditは現在使える残高。初期化・BET控除・WIN精算でrevisionを更新し、HTTP応答とともに返す。
- BETを受理する前にサーバーの残高を検証する。クライアントが送った減算後残高を正本として採用しない。残高不足、負額、不正な合計は拒否する。
- 参加者の `creditAfterBet` はサーバーで計算する。同じラウンドの同じBETを再送しても追加控除しない。BET受付中に額を変更した場合は差額だけ調整する。
- WINは記録済みの予約を基に一度だけ加算する。同じ精算の再送は同じ結果を返し、再加算しない。
- BETと残高の永続化を確認してから成功応答を返す。予約応答の直後に再起動しても、控除済み残高と参加情報を維持する。
- 初期化版を保存し、再読み込み・サーバー再起動・次ゲーム移行で100万に戻さない。

既存の旧walletも今回の暫定開始額へ一度だけ移行する。旧ゲームの未精算参加者が残っている場合は、その精算を終えてから移行する。成績やペイアウト率調整用の履歴を削除して残高を作り直す方式は使わない。

## 回帰テスト

`npm run check` と `npm run test:shared` を実行する。追加分は `npm run test:sync` にも含める。

- `shared-v228-wallet-hydration.mjs`: 同revisionの残高復元、古い財布の拒否、BET成功／不足応答、精算ACK、正規化済みBET内訳。
- `shared-v228-credit-rebet.mjs`: 実Arcade・core・controller・配当処理を9枠で実行。初期100万、27,000控除、2回連続WIN精算、重複応答、明示0、灰色ボタン、手動BET、未開始のまま終了した予約のロック解除。
- `server-wallet-v228.mjs`: 隔離した実サーバーで初期化、27,000予約、同一要求の再送、増減差額、残高不足、WIN加算、精算再送、再起動、旧wallet移行を確認。

これらは実際の制御コードと隔離した実サーバーの検証であり、利用者のWindows実機に更新が適用されたことを示すものではない。

## Windowsサーバーへの反映

今回はサーバー側の残高処理も変更しているため、GitHub Pagesの更新だけでは完結しない。Windowsのプロジェクトを最新mainへ更新し、`start-shared-machine-tunnel.cmd` からサーバーを再起動する。`.runtime`・`.tools`・`data` は保持する。特にデータ削除で残高を初期化しない。

更新後、ホスト画面とプレイヤー画面を再読み込みする。公開クライアントの版表示は `20261116-v228-credit-auto-rebet`。サーバーの初期化は一度だけで、2回目以降の読み込みは直前の残高から再開する。
