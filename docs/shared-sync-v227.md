# v227: BET終了後にNEXTへ戻り、クライアントが開始しない問題

更新日: 2026-11-16  
クライアント版: `20261116-v227-bet-start-recovery`

## 再現した原因

1. `joinBet()` が結果通信とは別に映像の `isFresh()` を必須としていた。結果WebSocketと状態取得が正常でも、映像が止まる・RTC/relayが利用できない端末ではBET登録が行われない。一方、時計はサーバーの `canBet` だけでカウントを表示し、PLAYINGになって参加者がいないとNEXTを表示した。
2. 接続の安定確認中に見えたBETを `blockedRoundId` に固定していた。サーバーが参加可能と判断し、接続も安定し、締切まで十分な時間があっても、最初のBETだけは参加できなかった。実サーバーを起動した試験でも再現した。
3. サーバーがBET登録を受け付けた後にHTTP応答だけ失われると、次の状態取得で見つかった参加者を古い未処理ラウンドとして0WINで破棄した。参加を申し込んだ現ページの要求と、以前の参加情報を区別していなかった。

## 修正

- BET参加を結果通信とサーバーの資格判定に基づかせ、映像の受信・再接続から独立させた。登録後の開始も映像の一時停止で止めない。
- 安定確認中に見たという理由だけでBETを拒否する判定を削除。安定接続、正常な状態取得、初期化済み盤面、サーバーの `canBet=true`、締切まで2.2秒以上、BET額と残高の確認は維持する。BET開始後に接続した参加資格のない端末は、従来どおり次のBETを待つ。
- 現ページ・現接続で送ったBET要求のトークン、ラウンドID、ソケット、接続世代を追跡する。HTTP応答が失われても、それらに一致するサーバー参加情報で登録を確認し、開始する。同じ要求の再送は同じトークンと内容を使用する。
- 異なるトークン、別プレイヤー、別ラウンド、切断後の接続、既に精算された参加情報は復旧対象にしない。途中切断ゲームの再演は追加していない。
- BET時計に「BET登録待ち」「BET登録を確認中」「BET登録済み」「再試行待ち」「CREDIT不足」など、実際の参加状況を表示する。受付中のカウント表示を登録完了とは扱わない。
- 前版の標準1倍速と初回入賞前の誤リセット対策を維持する。

## 検証

`npm run check` と `npm run test:shared` を使用する。追加した回帰は `npm run test:sync` にも含める。

| 回帰 | 実行する実コードと確認対象 |
| --- | --- |
| `shared-v227-registration.mjs` | 実映像モジュールと実controller。RTC/relayが使えず映像freshness=falseでも2回連続でBET・開始・通常精算・次盤面へ進む。開始直前の映像切断でも結果処理が継続する。 |
| `shared-v227-bet-reservation.mjs` | 隔離した実Nodeサーバー、実ClientのHTTP/accept、実Arcadeの開始処理、実controller。最初の適格BET、参加資格のない後入り端末、古いPOST応答と新しい個別snapshotの前後、公開WS通知のparticipant補完を確認する。 |
| `shared-v227-client-install.mjs` | 実ゲーム本体のEngine/Choco/Candy/Arcade、通常パッチ、native draw source、共有core全体のinstall、配当wrapper、controllerを実行。遅延ACK、ACK消失、最初の3球の配送、異なるトークンと接続切替の除外を確認する。 |

単純な開始関数の置換だけで確認せず、`drawSource.ready` と開始ラッパーを実際にインストールする試験を追加した。描画や映像品質、利用者のWindows実機での動作確認とは区別する。

## 反映

今回の動作変更はプレイヤー側JavaScriptであり、Nodeサーバーやホスト物理処理の変更はない。GitHub Pagesのプレイヤー画面は公開完了後に再読み込みする。Windowsサーバーから直接プレイヤー画面を開いている場合は、更新したクライアントファイルをその配信元にも反映する必要がある。

v226のWindowsホスト更新をまだ行っていない場合、v227のPages公開だけでは以前の初回入賞前リセット対策はWindowsホストへ届かない。既にv226を反映したWindowsサーバーは、この修正のためだけに再起動する必要はない。
