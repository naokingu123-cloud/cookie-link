# シックスドロップ v280 — 瓶への収まり・消去累計・丸い配当

> **未マージの検証候補（PR #5）**
> 作業中に main へ v281 (`004f088b`) が先行公開され、同じ依頼の Six Drop 変更と追加の音声更新が入りました。この枝は公開していません。以下の配当表・P/O・検査結果は、この枝の候補だけの記録です。公開 main の revision 280 は一部の配当が異なるため、この枝の表や UI をそのまま差し替えないでください。公開仕様は main の docs/sixdrop-v280.md を正とします。

版: `20261120-v280-sixdrop-fit-and-round-payouts`。2026-11-20の追加依頼に対応する。シュガーの透過倍率・開始前の旧条件移行を含むv279の上に重ねる。

## 画面の変更

旧瓶の蓋と側枠は、以前の `.game > .field::before / ::after` が新しい瓶の下にも描画されていた。v278の片側だけの弱い上書きを改め、両方の描画を確実に止める。キャンバス背景に残っていた旧い白い角丸輪郭も除き、新しい透過PNGの瓶だけを使う。元のお菓子の世界背景と、実際のドロップ素材は維持する。

ドロップの共有座標の間隔を27.745から29.4へ、直径も約5.96%拡大し、中心Yを158にする。静止時の揺れも含めて75位置が瓶の透明な内側へ収まるようにする。メイン、mini、落下、リーチ、成立線は同じ座標を使う。既存の素材PNG5枚は生成し直さず、バイト単位で保持する。

全消しの見出しは瓶の幅に収め、ロゴと金額を隣接させる。背後の水色の枠・ガラス調の囲みを除く。金額が増えても数字だけを枠内へ収め、少額のときに金額の左へ大きな空白を作らない。3・2・1・1・1球の表示は削除するが、実際の5群の抽選・消去・補充手順は変えない。

瓶の下に「消去合計」を表示する。配当表は成立個数を `×1`、`×2`…と表示し、役の図は盤面と同じドロップで描く。直線は4個の並び、三角は6個の3段配置、ヘキサゴンは6個の輪を示す。

## 消去合計と継続

新しい保存カウンターは作らず、既存の `state.removedTotal` と `carry.removed` を使用する。表示値は全消し額の既存カウントアップ時計から算出し、消去に合わせて同じタイミングで増える。表示の更新によって消去数や配当を加算することはない。

- 全消しを獲得しても、累計消去数と全消し蓄積額は保持する。
- 次ゲームにも継続し、100個ごとの次ゲームの4色構成も維持する。
- シックスドロップ自身が正常に8球を終えてWIN 0だった場合だけ、既存の規則どおり初期化する。
- 途中の再読込では保存された数へ戻し、既に計上した消去を再加算しない。

消去1個ごとの全消し蓄積額 `BET × 0.05` は変更しない。

## 役の配当

新しく始めるゲームはrulesRevision 280を使う。個数別の累計配当を読みやすい倍率へ整え、個数が増えるほど増分が下がらない性質を維持する。配当表と実精算は同じ関数を参照し、役ごとに整数WINを確定してから合算する。

100 BET時の累計配当は次のとおり。

| 成立数 | 直線 | 三角 | ヘキサゴン |
|---:|---:|---:|---:|
| ×1 | 20 | 50 | 100 |
| ×2 | 50 | 200 | 400 |
| ×3 | 150 | 400 | 800 |
| ×4 | 250 | 700 | 1,400 |
| ×5 | 400 | 1,100 | 2,200 |
| ×6 | 550 | 1,600 | 3,200 |
| ×7 | 750 | 2,200 | 4,400 |
| ×8 | 950 | 2,900 | 5,800 |
| ×9 | 1,200 | 3,700 | 7,400 |
| ×10 | 1,500 | 4,500 | 9,000 |

10個を超える場合も同じ増加規則で計算する。旧revision 248の単球ルール、旧revision 278の群進行・配当、途中状態、録画のRNG・盤面・金額は保存時の版を使用する。群進行の境界278と、新配当の境界280を分けて判定する。

## 配当調整の検証

支持確率 `.23 / .57 / .615 / .9` は維持した。配当だけの丸めによる影響を、同じ盤面・RNG・消去・全消し額のまま新旧で比較した。公開v278の独立32,000ゲームを新表で再評価した平均は、設定50/90/100/150の順で49.261875% / 90.559375% / 98.245625% / 152.104375%。旧表からの増加はそれぞれ0.08375 / 0.35875 / 0.43125 / 0.63625ポイントだった。

別seedの新規20,000ゲームでは、設定50は2,000ゲームで46.765%、90は8,000ゲームで99.715625%、100は8,000ゲームで107.544375%、150は2,000ゲームで159.755%。90/100の初期標本が上振れたためseedを置き換えず同じ系列を延長し、初期分との重複を数えていない。同じ標本の旧表との差は0.11 / 0.30375 / 0.33625 / 0.50ポイントで、標本変動に合わせた再較正は行わなかった。

これらはBET100・均等8/25抽選・継続ありのSix直接配当の標本平均であり、理論値や短期の還元率保証ではない。共通Sugar/JPC、物理抽選の偏り、他BET、サーバーのfeedback制御を含まない。旧標本の95%区間を新表へ流用していない。seed、標本数、block SE、core SHA、原集計は [配当検証原本](qa-v280/payout-validation.json) と同ディレクトリのJSONLに保存した。

## 検証・公開

ルール、整数配当、消去カウンター、旧保存互換、台帳・精算のローカル検査を行う。専用CIでPC・390px・miniの実表示、実Download workerの8球と9チェックポイント、公開ファイル30件のHTTP200・byte数・SHA-256を確認する。結果と実画面は完了後に追記する。

最初の候補 `d162595d` のCI `44754825393` はrules/legacyと実Download workerに成功したが、UIのPNG内窓検査で停止した。テストと事前の画像検査が10段盤面の7/8個の行幅を逆にしていたうえ、正しい75点でも最下段8個の両端がalpha253の縁へ接触していた。30.2/中心163の拡大案を29.4/中心158へ修正した。検査はnativeの行幅を使用し、oracle盤面の各行数との一致も確認する。1.02倍の呼吸と±0.9pxの揺れを含めた最大alphaは72、最下段両角は41/47で、閾値80は維持した。失敗時にも実測を保存するようにし、初回の失敗証跡も保持する。

修正候補 `c6ba373` のCI `44755794333` はrules/workerに加え、UIのready復元・実8球・390px配置の3ケースも通過した。最後のmini検査は、正常な結果表示の自動次ゲーム遷移後に獲得badgeを期待して失敗した。診断ではphase ready・state null・獲得回数0・継続累計234で、正しい次ゲーム状態だった。`stopResultAuto()`は一度timerを消すだけで、通常の次UI更新から再開するため、検査の結果保持条件が成立していなかった。スマホの画像もRESULTモーダルに覆われていた。そこでスマホ・miniの検査と撮影を、初回全消し後の5球の手動待機境界へ移動し、元のPC盤面へ戻して残り3球を完走させる。runtimeの自動復帰・配当・進行は変更しない。2回目の失敗原本も保存する。

Windows上の稼働サーバーへの適用・再起動はWeb公開とは別で、今回も未実施。サーバーに新しい配当を適用する際は最新ソースを反映して再起動し、`.runtime`・`.tools`・`data`を保持する。
