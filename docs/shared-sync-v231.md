# v231: サーバー映像専用クライアント

更新日: 2026-11-16  
版: `20261116-v231-remote-roulette-only`

## クライアントで抽選機を作らない

プレイヤー画面と精算workerでは、`loadCookieRoulette`が3Dモジュールを読み込む前に戻る。ローカルのrenderer・物理world・抽選clockを作らず、再読込ボタンから呼ばれても生成しない。`serverHost=1`の配信画面だけが従来の実物理抽選機を起動する。

プレイヤーの表示領域はBET TIMEからゲーム終了まで同じサーバー映像を使う。古いローカルcanvasは表示しない。未受信時は接続待ち、受信後の途切れでは最後の実フレームと再接続表示を出す。クライアント独自のBET演出や抽選映像へ切り替えない。

## 配信再接続の分離

旧WebM relayは、新規視聴者へ先頭ヘッダーを渡すために共有MediaRecorderを再起動していた。他の視聴者もそのたびにdecoderを作り直す経路があった。

新ホストは`rtc_host_ready.frameRelay=1`を通知し、直接WebRTC映像が使えない場合に、同じ表示canvasから生成する独立JPEGフレームを配信する。最大15fps・720×405内・quality0.70で1回だけencodeし、必要な視聴者へ共有する。新規接続やパケット欠落で既存視聴者の映像を再起動しない。直接WebRTCは従来の30fps設定を優先し、正常再生時には追加JPEG購読を止める。

画像はdecode成功後に表示する。decode中は最新1フレームだけ待機し、古いフレームを蓄積しない。表示imgを再利用し、毎フレームのDOM追加削除も避ける。ホスト・受信先のWebSocketが詰まった場合は古い画像を送信queueへ追加しない。新しいホスト・接続instance・sequenceを確認し、古いフレームによる巻き戻しを防ぐ。

中継サーバーは登録済みホストからのJPEGだけを受け付け、指定プレイヤー・指定instanceへ転送する。旧サーバー・旧ホストとの更新順序に備えて従来WebM経路も互換用に保持する。新経路を使うにはWindows側のサーバーとホスト画面も最新版への更新が必要。

## 検証

- 実`loadCookieRoulette`をプレイヤーとして2回呼び、module loaderとrenderer生成が0回、ホストとして2回呼ぶ場合は従来の生成処理が動くことを確認。
- 画像decode前は未表示、decode後に表示、100フレームの到着中もdecode待ちを最新1枚へ集約し、表示imgが1個のままであることを確認。
- ラウンドをまたいだ表示、古いホスト/sequenceの排除、最後の実画像の保持、WebRTC復旧後のJPEG停止を確認。
- 3視聴者でencodeを共有し、途中参加で既存視聴者へstopを送らないこと、送信詰まり時に画像を蓄積しないことを確認。
- 実Nodeサーバー/WebSocketで新しい通知・購読・JPEG転送・購読停止・宛先分離・未登録送信者拒否を確認。
- `npm run check`と`npm run test:shared`で既存の物理抽選・同期・BET・WIN・結果後の操作復帰を確認する。
