## 1. 新規ゲームの処理

新しく開始するゲームは、番号を受け取るたびに1球ずつ処理する。8球の進行は `1・1・1・1・1・1・1・1` となり、最初の3球や次の2球がそろうまで消去を保留しない。

HITしたドロップ自身と、その六角格子上の隣接位置に実在するドロップを消去する。中心1個に対する周囲は最大6個で、合計最大7個。色の一致は最初の周囲消去の条件にしない。盤面の端、空いている位置は対象から除く。同じ消去範囲が重なった場合も、1個のドロップを二重に消したり原資へ二重加算したりしない。

1球の中では、HIT判定、中心と周囲の消去、落下、同色4個以上のつながりや役による連鎖、全消し判定、補充の順に処理する。直線・三角・ヘキサゴンが成立した色をすべて消す規則は継続する。補充はその1球の末尾で最大1回とし、予測表示では補充用の乱数を進めない。実際の結果は表示アニメーションより先に保存するため、消去演出の途中で保存しても、復元時に同じ配当を二度計算しない。

HITの光は当選番号の中心セルへ出し、周囲も含む消去は既存の `pyramidBreak.removed` の演出へ渡す。新しい `pyramidHit.affectedCells` には重複のない実タイル座標を記録する。旧ルールのタイムラインへこの新フィールドを追加することはしない。

実装: [ルール](../assets/sixdrop-progressive-core-v247.js)、[ホスト](../assets/sixdrop-progressive-host-v247.js)。

## 2. 保存済みゲームの互換性

途中保存の `state.rulesRevision` が処理方法と配当を決める。読み込み時に新ルールへ書き換えず、そのラウンドを元の規則で8球まで完了した後、次の新規ゲームから283を使う。

| 保存されたrevision | 1ラウンドの処理 | 最初のHIT消去 | 配当 |
|---|---|---|---|
| 248 | 1球ずつ、合計8回 | 旧ルールの番号一致セル | 248の旧配当 |
| 278 | 3・2・1・1・1球 | 旧ルールの番号一致セル | 278の旧配当 |
| 280 | 3・2・1・1・1球 | 旧ルールの番号一致セル | 280の丸い配当表 |
| 283 | 1球ずつ、合計8回 | 中心＋存在する周囲最大6個 | 280の丸い配当表を維持 |

`CURRENT_REVISION` と `SINGLE_REVISION` は283、`ROUNDED_REVISION` は280、`GROUPED_REVISION` は278。単純な `revision >= 278` をまとまり処理の判定に使わず、`isGrouped(stateOrRevision)` で処理方法を選ぶ。`batchSize(processed, stateOrRevision)` には保存状態またはrevisionを渡す。互換性のため、既存の `BATCH_SIZES` とrevision省略時の `batchSize` は従来のまとまり処理の契約を残す。

248/278/280の変更前の9例は、初期状態、全状態、各タイムライン、乱数カーソル、配当をまとめたSHA-256が一致する。278/280の1・2・4球時点の未解決番号や、完了済みの3球・2球queueも維持する。248の古い保存で数値RNGが欠けた場合だけ、保存seedと履歴からの再計算が盤面と既存配当を完全に再現できる条件で回復する。283の欠損RNGを推測で補完しない。

既存のファイル名 `sixdrop-progressive-*-v247.js`、`sixdrop-ui-v278.*`、`SixDropV247` / `SixDropUiV278` などのAPI名は参照互換性のため維持する。UIの内部versionは283。

## 3. 固定HUDと盤面寸法

「全消し」、金額、`WIN`、継続表示は幅290 pxの同じ行に配置する。金額の桁数が増えてもロゴや `WIN` の位置を動かさず、金額の文字だけを割り当てた枠内へ収める。継続表示が非表示の間も、その列の幅を予約する。

| HUDの領域 | 論理CSS幅 |
|---|---:|
| 全消しロゴ | 76 px |
| 金額 | 136 px |
| WIN | 24 px |
| 継続表示 | 32 px |
| 3か所の列間隔 | 各2 px、合計6 px |
| 左右の内側余白 | 各8 px、合計16 px |
| 合計 | 290 px |

金額列はCSS Gridの残り幅で、290 − 76 − 24 − 32 − 6 − 16 = 136 pxとなる。表示金額から枠自体の幅を伸縮させない。モバイルでは画面全体の倍率に従って縮小されるため、上表の論理CSS寸法とスクリーンショット上の実ピクセル数は区別する。

| 領域 | 論理CSS寸法 |
|---|---:|
| 共通ゲーム領域 `.game` | 高さ390 px |
| 全消しHUD | 幅290 px、高さ52 px |
| 盤面領域 `.field` / パネル / 配当表 | 高さ312 px |
| 瓶 | 幅290 px、高さ290 px |
| 瓶直下の消去合計 | 幅290 px、高さ22 px |

瓶290 pxと消去合計22 pxを盤面領域312 pxに収める。旧瓶の側面枠・反射線・水色の外枠を再表示しない。消去合計は全消し原資と同じ増加過程に同期し、最後に実際の累計へ一致する。配当表の `×n` 表記と実ドロップによる直線4個・三角6個・ヘキサゴン6個の図形を維持する。

上記は[CSS](../assets/sixdrop-ui-v278.css)と[UI実装](../assets/sixdrop-ui-v278.js)の仕様。CUAで実画面を確認し、Cookie/Gelato/Sixの外枠は同じ390 px、5桁から6桁の増加途中でもロゴとWINの座標は一致した。390 px幅のiframe表示でも瓶・配当表・消去合計が収まった。座標は [CUA記録](qa-v283/sixdrop-v283-cua.json)、表示は [PC画像](qa-v283/sixdrop-v283-desktop.jpg)と[390px画像](qa-v283/sixdrop-v283-mobile.jpg)を参照。8球通しの自動ブラウザー検査と公開検査は別途確定する。

## 4. 配当・原資・精算

今回、役配当表、消去1個あたり **0.05 BET** の全消し原資、全消し後も原資を継続する規則は据え置く。新規283の直線・三角・ヘキサゴンの配当は280と同じで、役ごとに小数メダルを切り捨てた金額へ全消し配当を加算する。配当表と×6以降の式は [v280の配当仕様](sixdrop-v280.md#役配当)を参照する。

原資への加算対象は、実際に消えたドロップだけ。周囲消去、連鎖、役による同色消去のいずれでも1個につき1回だけ加算する。全消し時の配当はその時点の原資の整数メダル額であり、その支払いによって蓄積原資を消費しない。

正のWINで完了したゲームの原資、累計消去数、色の進行を次へ持ち越す。BET変更時も既存の原資を再評価せず、新しい消去分だけ新BETで加算する。途中中断、未精算のゲーム、非参加では既に確定した持越しを保持する。**そのSix Drop自身が8球を完了して0 WINになった場合**に原資・累計消去・色の進行をリセットする。他ゲームにWINがあってもこの判定は変わらない。

録画、共有checkpoint、Download worker、offline settlement worker、サーバー精算のruntimeは今回変更しない。保存状態からホストが正しい `drawMode` を再構築し、既存経路で再開・8球完了・精算を行う。重複した精算通知では二重入金せず、管理側の取り消しではBET前の原資とwalletへ戻す。

## 5. P/Oのpilot測定と未較正事項

**旧280の較正値を283へ流用できない。** 周囲消去と毎球補充により、盤面の推移、連鎖、全消し、0 WINになる頻度、継続原資の履歴が変わる。旧役成立数ヒストグラムの配当だけを置き換える方法では比較できない。

担当者が確定した測定原本は [sixdrop-payout-impact-pilot.json](qa-v283/sixdrop-payout-impact-pilot.json)。4設定率 × 旧新2revision × 通常/補助なし2モードの16条件、各256ゲーム、合計4,096ゲームを実行した。BET100、対応する盤面seedと25番号から重複なしで8番号を選ぶ乱数列を共用し、各条件内では正のWINによるcarryを連続して保持している。

| 設定率 | 旧280・通常モードの観測P/O | 新283・通常モードの観測P/O |
|---:|---:|---:|
| 50 | 34.473% | 3,653.672% |
| 90 | 97.285% | 4,924.453% |
| 100 | 107.852% | 4,963.105% |
| 150 | 118.633% | 5,423.281% |

設定90の283は通常役配当372.070%と全消し配当4,552.383%を合わせた値。補助テンプレートと番号位置の優先付けを外す研究用モードでも283は2,493.750%だった。このpilotでは、補助だけを取り除いても設定率90相当には戻らなかった。

これは仕様変更による大きな差を検出するための短いシミュレーションであり、最終較正値や長期RTP保証ではない。carryによる依存と長い連勝の影響があるため、各ゲームを独立標本とみなした信頼区間を主張しない。共有Sugar/JPC、実ルーレットの偏り、適応的な払い出し制御も含まない。**設定値90を実測90%として扱うことはできない。**

runtimeの役配当表・0.05 BET加算・carry・補助設定をこの測定に合わせて変更してはいない。追加標本と再較正は未実施。測定結果を公開環境の検証完了や公開済みの証拠として扱わない。
