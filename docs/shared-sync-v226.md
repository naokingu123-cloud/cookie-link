# v226: 初回3球より前の誤リセットを修正

更新日: 2026-11-16  
クライアント版: `20261116-v226-preserve-first-draw`

## 再現した原因

ホストの復旧監視は、最後の入賞から壁時計で15秒経過すると物理抽選機をリセットしていた。球が飛行・転動中か、シミュレーションが正常に進んでいるかは確認していなかった。

さらに `shared-host-speed-v219.js` は、BET中にも付ける表示用の `serverLockedSpeed=2` を実際の2倍速設定済みと扱っていた。実エンジンの速度は内部変数なので、この状態では通常のBET→PLAYINGで1倍速のままになった。

配信している `optimized/app-01.js` から実際のCANNON、RoulettePhysics、DrawControllerを抽出して実行したところ、標準seed 8013では発射が物理時間0 / 2.0083 / 4.0167秒、最初の入賞が16.5333秒、3球の入賞完了が19.2417秒だった（faults=0）。したがって15秒の監視は正常な初回入賞より先に発火する。低FPSでも壁時計だけが先に進むため同じ誤判定が起きる。

## 修正

- ユーザー指示により強制2倍速を廃止し、標準の1倍速に統一。倍速ボタンを非表示・無効にし、以前の2倍速状態があれば実際の制御APIまたはネイティブボタンで1倍速に戻す。表示用フラグを実速度の根拠にしない。
- ホストの監視を物理時刻、発射数、稼働球数、入賞数、抽選段階の進行に変更。正常に進行している間は、入賞が15秒を超えてもリセットしない。
- 通常の500ms監視や状態通知のたびに `setPaused(false)` を呼ぶ処理を除去。これは物理時間の蓄積と描画予約を毎回消す副作用があった。
- 物理状態が止まった場合はまず描画を再開し、60秒以上進行がなく、再開要求後にも猶予を置いた場合だけ復旧する。非表示の時間はリセットの理由にしない。
- 入賞送信が一時的に失敗しても、同じ入賞結果を保持して再送し、飛行中の球をリセットしない。物理8球の試行が完了し、送信待ちがなく、サーバーの未入賞分がある場合だけ次の物理試行へ進む。
- クライアントの共有抽選への接続待ちと映像待ちを見直し、正常な開始処理を短すぎる期限で破棄しない。中断後に遅れて届く開始応答が旧ラウンドを再作成しないようにする。
- 実際のArcadeでは `drawHeld` はgetterのみ。復旧処理がこの値へ代入して例外になる箇所を除去し、実クラスに沿って初期化する。

## 検証と範囲

`npm run check` と `npm run test:shared` を使用する。新しい `shared-v226-host-start.mjs` は配信中の物理コードと実ホスト同期処理を実行し、初回の入賞を待てること、非表示・停止・送信再試行を区別できることを確認する。`shared-v226-client-start.mjs` は実Arcadeと共有開始処理を使い、開始待ちから最初の3球までの進行を確認する。既存の配当回帰もgetterのみの `drawHeld` で実行する。

サーバーについても、0球および2球のまま15秒以上経過させ、精算・leave・ホスト切断があっても同じPLAYINGを維持し、8球目で初めて完了・次BETとなることを隔離起動で確認した。

この試験は実際の物理・制御コードの実行による検証であり、Windows実機上の描画速度や映像品質を測定したものではない。

## Windowsへの反映

既存サーバーを停止し、最新mainのファイルを現在のプロジェクトへ上書きして `start-shared-machine-tunnel.cmd` から再起動する。`.runtime`、`.tools`、`data` を保持する。ホスト監視画面とプレイヤー画面も再読み込みする。

今回の主要修正はホスト側のブラウザで動くJavaScriptにも含まれるため、GitHub Pages側だけの更新では不十分。Windows側のファイル更新とホスト画面の再読み込みが必要。
