# シュガーチャレンジ v254

## 対象

版は `20261119-v254-sugar-challenge`。既存10ゲームと共有サーバーの8球抽選を維持し、5個のシュガーから始まる共通チャレンジを追加する。ダンゴとタブ表示の変更は `docs/dango-v254.md` を参照。

## 進行とJP

- シュガーを5個集めると、次のBET時間にシュガーチャレンジを開始する。獲得・消費・進行はプレイヤー別サーバー台帳に保存する。
- シュガー1個の内部額は、獲得したゲーム自身のそのラウンドのBET×10を基準とし、獲得時のP/O設定（50〜150%）と0.8〜1.2の一様な揺らぎを掛ける。整数メダルへ四捨五入する。通常画面の既存シュガー表示額とは別に保持する。
- 5個を順に生成画像の秤へ投入し、合計額を連続して増やして表示する。同額BET・P/O100%で倍率適用前の平均JPはBET×50。
- 続く倍率ルーレットは1倍80%、2倍15%、3倍4%、5倍0.9%、10倍0.1%。平均倍率は1.275なので、同条件の倍率適用後の平均JPは端数丸め前でBET×63.75となる。
- 内部額、カード、倍率はチャレンジの最初の球より前に決定・保存する。表示演出や後続の抽選結果による再抽選はしない。
- メイン表示は通常ゲーム上の暗い半透明背景へ重ねる。魔法の瓶、配当、JPC条件、投入量とルールを表示する。タップで抽選機付近の小表示へ切り替え、再タップで戻せる。
- 入賞番号の数だけ瓶の量を増やす。共有サーバーから届く重複のない8球を使用し、8球目で合計値と配当を確定する。クライアントの独自8球抽選は追加しない。

## カードと合計数字

ラッキーナンバーは「8球の合計数字」。個々の入賞番号ではない。各カードの低側・高側JPC区間の間に置き、その合計と一致するとJPC権利を得る。

|カード|出現率|低側JPC|高側JPC|ラッキーナンバー|
|---|---:|---|---|---|
|シュガーカード|90%|36〜70|138〜172|77・88・120・131|
|ラッキーシュガーカード|5%|36〜70|138〜172|77・88・99・109・120・131|
|ワイドシュガーカード|5%|36〜78|130〜172|88・120|

上記出現率は約10%の合算JPC確率に合わせた実装上の設定。レアカードはラッキー合計の数が多いものと、両端のJPC区間が広いものの2種類。

JPC以外の配当はJP×0.2／0.1／0.05／0.03／0.02／0.01。合計104から離れるほど高配当になる。ラッキーナンバーは通常配当区間より優先する。最終配当は整数メダルへ切り捨てる。正確な分割区間と全合計の度数は `docs/sugar-challenge-v254-probabilities.json` に収録。

## 確率

1〜25から重複なく一様に8個を取るモデルの全1,081,575組合せを独立に列挙し、動的計画法の分布と照合する。最小合計は36、最大合計は172、中心は104。

3カードを混合したJPC権利の成立率は **9.997938191988535%**。これはシュガーチャレンジ開始後の条件付き確率であり、シュガー5個の獲得頻度や全ゲームの総P/Oではない。実物抽選機の偏りはこの計算に含まれない。

JPC本体は今回の依頼どおり未実装。成立したJP額・合計・最後の入賞番号・理由を未消化のJPC権利としてサーバーに保持する。JP額そのものを通常配当として支払わず、JPCの将来価値を通常配当期待値へ加算しない。

## 共有進行と互換性

- シュガーの受領ID、消費済み5個組、チャレンジ、通常ボーナス入金、JPC権利を保存し、同じ通知の再送で二重消費・二重加算しない。
- チェックポイント、通常クライアント精算と切断中のサーバーworker精算へシュガー情報を引き継ぐ。通常ゲームのWINとチャレンジのボーナス入金を分けて計上する。
- 7球時点のJPCリーチ番号は共有抽選機で赤数字と席色の枠を表示し、成立時は虹表示にする。受信順の逆転によって確定表示が7球時点へ戻らず、次のラウンドで消去する。
- メニュー、非表示、動きを減らす設定では表示演出を抑える。サーバー抽選、配当、次BETの進行を表示待ちにしない。
- 従来の持越しシュガーとrevision251／253のダンゴ途中データを保持する。既存のWindowsランチャー設定を維持する。

## 検証と公開

ルール・分布の再現は `npm run test:sugar`。実サーバー上のフロー、独立した抽選機表示、実ブラウザの表示・操作を含む検証を同じ版に対して実施する。最終結果は別途QA記録へ記載する。

GitHub Pagesの公開はWindows共有サーバーのローカルソースを更新しない。Windows側は最新mainの全ソースを反映し、`.runtime`・`.tools`・`data`を保持して既存ランチャーから再起動する。Windows／iPhone実機とスピーカー聴感は今回の自動検証の対象外。
